v4.5.1 (March 9, 2026)

  Highlights:

  - Rules from the Fortran Linter Fortitude have been applied.
    (https://github.com/PlasmaFAIR/fortitude)

  - Addressed warning messages in examples when compiling with nagfor.
    
  General:

  - Code improvements have been applied as suggested by the rules from
    the Fortitude linter. The following rules have been addressed:

    * Remove trailing whitespace (fortitude rule S101).
    * Fix trailing backslash in comment lines (fortitude rule C051).
    * Replace old array notation (/../) with [..] (fortitude rule MOD011).
    * Fix missing exit/cycle label (fortitude rule C141).
    * Fix unnamed end statement (fortitude rule S061).
    * Fix deprecated relational operators (fortitude rule MOD021)
    * Initialise pointer variables inside derived types (fortitude rule C101).
    * Always include "case default" in select case (fortitude rule C011).
    * Specify intent for all arguments (Fortitude rule C061)
    * Add 'implicit none' in interface definition (Fortitude rule C002)
    * Add intrinsic modifier to "use iso_fortran_env" (Fortitude rule C122)
    * Limit line length to 80 for core and add-ons (Fortitude rule S001).
    * Fix local variables initialised in the declaration (Fortitude rule C081)

    Although the changes are mostly cosmetic, the last rule (C081)
    can affect the runtime code behavior:

       Local variables that are initialised in the declaration
       automatically get the save attribute in Fortran. This can have
       unexpected effects if a routine is called more than once. Therefore,
       these variables should either get the save attribute explicitly,
       defined as parameters or initialised by a separate assignment
       statement, depending on their intended use.

    Limiting the line length to 80 characters (Fortitude rule S001),
    only applies to the core and the add-on files. Examples and test
    files can have lines as long as the Fortran standard allows. For F2023
    the maximum line length is 10,000.

    NOTE: We have ignored the following Fortitude rules:
    * C003: Checks if implicit none is missing external.
    * C121: Checks if only: is used in the use statement.
    * C131: Check whether modules contain public/private statements.
    
  Examples:

  - Addressed warning messages in examples when compiling with nagfor.
    The most frequent warning message was related to the use of global
    variables as a do-loop index. It is better to restrict do-loop indices
    to variables defined in the local scope to avoid changing global
    variables that might be used in the global scope as well.

v4.5.0 (December 22, 2025)

  Highlights:

  - Improved checking of coefficients. Most user codes that use the
    stokes/viscoelastic add-on will probably print error messages and
    REQUIRE UPDATING, i.e.
     * increase the size of the integer and real coefficients arrays,
     * move the viscoelastic material data to the free range.

  - The viscoelastic material data can now be stored as 2D arrays
    in the structure coefficients.

  General:

  - Improved checking of the integer and real arrays in coefficients,
    because of the following problems:

      * In version v4.0.0 of TFEM the range of coefficients in the
        stokes and viscoelastic add-ons have been extended to
        1:150 (integer) and 1:100 (real). Since we are now starting
        to use integers beyond the previous limit of 100, existing
        codes might show out-of-bound problems.

      * The viscoelastic model parameters were usually stored in
        a range of the real coefficients that belong to another
        add-on.

    Starting with this release an error message is given if the size of
    the coefficients is lower than the new required values and/or if
    the viscoelastic model parameters are stored in an illegal range.
    To get rid of those error messages, the user should:

      * increase the size of the integer and/or real arrays in
        coefficients. See the file README.coefficients in the 
        src/addons directory for the required sizes,

      * store viscoelastic model parameters in the free range 501:1000
        or in a 2D array of the new ra2 component of the coefficients.

  - All examples have been changed according to the new requirements
    for the coefficients. To show the changes in an example use git.
    For example to show the changes in the files in the example
    folder settling_sphere_b give the command from the root of TFEM:

         git diff v4.4.0 examples/settling_sphere_b

  - Type coefficients extended with arrays of 2D integer and real
    arrays (components ia2 and ra2 of coefficients). The 2D arrays
    are created with the ncoefia2/ncoefra2 keywords (see userguide).
    The main use of this extension is to supply the viscoelastic
    material data as 2D arrays (see below).

  Add-ons:

  - Viscoelastic material data can now be supplied to the elements
    using a 2D array in coefficients%ra2 having a shape of
    (npar,nmodes), where npar is the number of parameters per mode.

    The new interface is easier to use and cleaner and does not
    require the free range in coefficients%r to be allocated by
    the user. The number of parameters is therefore also not limited
    by the size of the free space.

    The new interface is activated by supplying a negative value to
    coefficients%i(20). Assuming m = -coefficients%i(20), the array
    containing the material data is coefficients%ra2(m)%a. Both the
    material_data and viscoelastic add-on have been adapted to support
    the new interface.

  Examples:

  - Removed legacy example energy2.

  - Added examples cylinder_egp1a and cylinder_egp7a showing the use
    of the coefficients%ra2 to supply the material data.

  Misc.:

  - Changed install files to using universal-ctags, a modern and
    maintained replacement for "Exuberant ctags".

  - Increased the free range of coefficients to 501:1000. This applies
    to both integer and real coefficients.

v4.4.0 (September 15, 2025)

  Highlight:

  - A full EGP model implementation with
      * global van Mises stress dependent relaxation
      * pressure dependent relaxation
      * elastic mode for strain hardening
      * plastic strain softening
      * explicit and implicit time stepping available
      * full Newton-Raphson iteration for implicit time stepping

  Add-ons:

  - New add-on material_data for easy filling of material parameters
    from a library of data. Currently, only the data of the EGP models
    from van Breemen et al. (2012) DOI: 10.1002/polb.23199 are
    implemented.

  - The adapted lambda model can now depend on the global von Mises
    shear stress. This means that the von Mises stress is based on
    the stress tensor of the sum of multiple modes instead of the stress
    per mode. In this way, the original multi-mode EGP model can be used.
    Both explicit and fully implicit time integration can be used.
    The modes can also be split into multiple "processes" each with a
    von Mises shear stress defined per process.

  - The adapted lambda model can now depend on the pressure. It is
    implemented as a factor h(J)=J^beta, dependent on the relative
    change in volume J. The function h(J) is consistent with the
    pressure dependent exponential function used in the EGP model.

  - With the argument norlxmode=m in create_viscoelastic_model
    the single mode m will have no relaxation added and therefore will
    act as an elastic mode. For the flow elements norlxmode is specified
    using coefficients%i(93).

  - The adapted lambda model can now depend on the equivalent plastic
    strain (gammap). It is implemented as a factor
         g(gammap)=exp(-Sa R(gammap))
    where Sa is the state parameter and R(gammap) is a softening function
    consistent with the softening function used in the EGP model.

  - In the viscoelastic_models module the use of drhs has been changed:

    * argument drhs moved to structure vemopt
    * call create_vemopt with argument compute_drhs=.true. to allocate
      and activate component drhs
    * optional argument drhs still present, but is obsolete and prints
      an error message.

  - In the viscoelastic_models module the component drhs_mm has been
    introduced in the structure vemopt to deal with coupling between
    modes in the Jacobian:

    * call create_vemopt with argument compute_drhs_mm=.true. to allocate
      and activate component drhs_mm
    * drhs_mm is required to compute the Jacobian of the adapted lambda
      model that depends on the global von Mises stress (EGP model with
      global von Mises stress).
    * drhs_mm can also be used for models without mode coupling.
      The matrix drhs_mm becomes a matrix with drhs on the diagonal wrt
      to the mode indices.

  - A new module viscoelastic_models_gammap_m with routines to compute
    the equivalent plastic strain. It is currently based on a single mode,
    like in the EGP model.

  - In module viscoelastic_elements_implicit_m single mode routines are
    replaced with multi-mode versions, assembling multiple modes in one go.
    The multi-mode versions are designed to be compatible with the single
    mode version, i.e. old programs should still work.
    The multi-mode versions are required for applying Newton-Raphson for
    models having coupling between modes, such as the EGP model with global
    von-Mises stress.

  - New module viscoelastic_elements_gammap_m defining the evolution
    equation for the equivalent plastic strain gamma_p for the EGP model.

  - Post processing:
    * Option to output global von Mises stress.
    * Coefficient 95 for setting mode number for regime in SRM DP model.
    * Output of gammap.

  Examples:

  - All viscoelastic_models examples (startup,steady) that use drhs as
    an argument have been adapted to use vemopt%drhs instead.

  - Examples startup48, startup48_log and startup49 use the EGP model with
    a global definition of the von Mises stress (multi-mode) for standard c,
    logc and b formulation respectively. All use 3D models.

  - Examples steady1[4-7].f90: EGP model with multi-mode von Mises stress

  - In the folder confined_cylinder_egp new examples have been added:
      cylinder1a_mm
      cylinder_c1_mm
      cylinder8_mm.f90
    which use multiple modes and the use of the global von Mises stress
    in the EGP model.

  - In the folder confined_cylinder_egp the following example has been added:
      cylinder1a_mm_gammap
    which adds plastic strain softening to the example cylinder1a_mm.

  - In the folder confined_cylinder_egp new examples have been added:
      cylinder9
      cylinder10
      cylinder_c9
    which use an EGP model with two processes. Example cylinder10 has
    the option to take the off-diagonal zero blocks into account
    in the sparseness of the system matrix.

  - New example steady18 to test alamJ_model=1.

  - In the folder cylinder_in_box_egp new examples have been added:
      cylinder_egp4_hJ
      cylinder_egp6_hJ
      cylinder_egp7
      cylinder_egp7_hJ
      cylinder_egp7_hJ_gammap
    where the extension _hJ means the example include the factor h(J) in
    the relaxation term (pressure dependence) and _gammap denotes
    an extension with plastic strain softening.

    Examples cylinder_egp4_hJ.f90 and cylinder_egp6_hJ.f90 are extensions
    of the existing cylinder_egp4.f90 and cylinder_egp6.f90 examples.

    The examples cylinder_egp7, cylinder_egp7_hJ and cylinder_egp7_hJ_gammap
    use an EGP model for PMMA from van Breemen et al. (2012)
    DOI: 10.1002/polb.23199 having a 12-mode alpha process,
    a one-mode beta process and an elastic mode.

  - New examples in the folder viscoelastic models:
     startup50 to startup57
        using data for PMMA from van Breemen et al. (2012)
        DOI: 10.1002/polb.23199
        The examples differ in
         * the use of c or b-formulation
         * explicit RK2, implicit trapezoidal or BDF2 time integration
         * 13 mode (alpha process and elastic mode)
         * 14 mode (alpha process, elastic mode and beta process)
     startup58 to startup64
        various examples using EGP with plastic strain softening.

   - New examples uniaxial_stress_egp[1-4].f90 to produce stress-strain
     curves in compression for the EGP model, using data from
     van Breemen et al. (2012) DOI: 10.1002/polb.23199 for PMMA, iPP,
     PS and PLLA, respectively.

  Userguide:

  - Small update to the userguide about mode coupling in EGP.

  - Add description of new examples.

  - Add a subsection on pressure dependence of adaptive lambda. It
    describes the function h(J) and the relation to the exponential
    pressure dependance in the EGP model.

  - Add a subsection on plastic strain softening in adaptive lambda. It
    describes the function g(gammap) for the EGP model.

  - The structure of the Jacobian matrix including the plastic strain
    is discussed.

  Misc.:

  - BUG FIX: this affects all previously existing EGP examples in a flow.
    In the following examples (all examples using the EGP model in a flow)

      folder confined_cylinder_egp:
        cylinder1a.f90, cylinder3a.f90, cylinder6a.f90, cylinder7.f90,
        cylinder8.f90, cylinder_c1.f90, cylinder_c3.f90, cylinder_c6.f90,
        cylinder_c7.f90, cylinder_c8.f90,
      folder cylinder_in_box_egp:
        cylinder_egp1.f90, cylinder_egp2.f90, cylinder_egp3.f90,
        cylinder_egp4.f90, cylinder_egp5.f90, cylinder_egp6.f90,
      folder poiseuille:
        poiseuille5.f90, poiseuille6.f90

    the line

      coefficients%i(80) = alam_model ! adapted lambda

    was missing. This basically meant adapted lambda was not activated and

  - The core module limits_m now contains the logical
       USE_ADAP_LAMBDA_FOR_EGP_DET_STAB
    to set the use of lambda constant in the determinant stabilization

v4.2.0 (November 9, 2024)

  Add-ons:

  - Interface to the viscoelastic models has been extended using a
    structure vemopt to facilitate optional arguments to the models.

    * On the lower (mode) level the structure vemmod is used to pass
      optional arguments. The variable drlxmod, that was an optional

      components in the structure vemmod, without the code becoming

    * The dependence on the change in volume J for EGP model 24 has
      been implemented using vemopt.

  - In the viscoelastic models, the deformation part (i.e. the part
    with the velocity gradient) has been moved to a separate
    subroutine. In this way, this part can be reused for the implicit
    implementation for models with mode-coupling. Only applies to
    the standard and the b-tensor formulation.

  - EGP (Eindhoven Glassy Polymer) model for incompressible flow (model=23)
    and compressible flow (model=24).

    Notes:

    * The c, b and log c formulations are available in 2D, axisymmetric and 3D.

    * Newton-Raphson can be used with the c and b formulations.

    * The stress-implicit approach has not yet been implemented for the
      EGP model. Therefore either the stress-explicit or the fully coupled
      implicit with Newton-Raphson must be used.

    NOTE: The EGP model for compressible flow (model=24) is only
          available on the viscoelastic model level. The use of the
          EGP model 24 in a flow similation has not yet implemented
          and will be part of a future release.

  - Adapted lambda cases 4 (Eyring) and 5 (Ree-Eyring) for use with
    the EGP model, but can be used with other models also.

    NOTE: The Eyring and Ree-Eyring functions are applied per mode.
          This means that the von Mises stress is based on the modal
          stress. Eyring and Ree-Eyring functions based on the global
          von Mises stress create a coupling between modes. Coupling
          between the modes has not yet implemented and will be part
          of a future release.

  - USE_CONFORMATION_MODEL in the model limits_m has been disabled for now,
    because it is not working correctly.

v4.0.0 (December 7, 2023)

  This new major version is basically a "big cleaning". The impact for
  normal users will be minimal, since user programs should run unmodified.
  Exceptions include user programs using the bcf add-on (see below).

  However, during installation the following items should be taken
  into account:

  1. The files from the HSL2002 library now reside in the external folder.
     This means that for those that have a license to use HSL2002 should
     unpack the hsl2002.tar.gz file instead of the hsl.tar.gz in
     previous versions of TFEM.

  2. It is recommended to do a fresh install when upgrading to v4.0.0 from
     a previous TFEM version. Just doing a "git pull" will work, but you
     will have remaining folders and files from the previous version
     that are ignored by git. Doing a "make allclean" before "git pull"
     will help a lot, but you still might end up with remaining folders and
     files that should not be there anymore.

  Two new repositories have been created: tfem_legacy and tfem_experimental.

  The repository tfem_legacy contains legacy modules, add-ons and examples
  that have been moved from the main tfem repository.

  The tfem_experimental repository of tfem contains add-ons and examples
  that do not (yet) fulfill all the criteria needed for inclusion in tfem,
  but can still be useful. It consists basically of the contents of
  the experimental folder in previous versions of tfem.

  Moved to tfem_legacy:

  - All examples using sepran generated meshes.

v3.9.0 (November 1, 2023)

  Core:

  - Dependencies branch merged (not yet finished).

  - Optionally exclude partitions that contain just zeros (zero blocks)
    from the system matrix to reduce the memory requirements and
    possibly also reduce the CPU time for solving the system.
    See the new Section 3.5.7 in the userguide.

  Add-ons:

  - ncompg was used, even if DEVSS not set (fixed).

  - Moved DEVSS elements to the stokes add-on. DEVSS is a numerical trick
    to create stable low-order mixed Stokes elements.

  - Setting coefficients%i(30)=1 in the DEVSS-G elements does not
    multiply the equation
          nabla u - G^T = 0
    with alpha, leading to a non-symmetric matrix. In this way, G will
    still be properly defined if alpha=0. This is needed if the equations
    are solved fully implicit without DEVSS-G, but G is still needed for the
    constitutive equation (G-method).
    NOTE: this only applies to DEVSS-G, not to DEVSS-E.

  - New routine implicit_ce_timederiv_supg_elem in module
    viscoelastic_elements_implicit_m that builds the matrix of the
    time-derivative term only. It is needed for assembing a generalized
    eigenvalue problem for linear stability analysis.

  - Setting coefficients%i(30)=1 in the implicit_ce_supg_elem routine
    excludes the time-derivative term. This will built the Jacobian
    of the convection term and (minus) the right-hand side of the CE.
    Possible reasons for excluding the time-derivative term are:
    * Perform Newton-Raphson iteration for the steady state, if it exists.

v3.4.0 (February 20, 2023)

  Core:

  - IMPORTANT: The default in isoparametric_deformation has been set to
    output |detF| instead of detF. This avoids the erratic combination of
    detF<0 for domain integrals with curvel/surfl > 0 for boundary integrals
    in the discretized weak form. This could, for example, happen with gmsh if
    you define your 2D domain with curves ordered clockwise. Note, that
    the default can be changed (see below).

  - New settings in the limits module regarding the sign of detF.

    For "domain" elements (line in 1D, tri/quad in 2D, tet/hexa/prisma/pmid
    in 3D) the sign of detF in isoparametric elements is supposed to be a
    positive value. Sometimes, however, you end up with a negative sign for
    detF. For example, when you define a 1D mesh with decreasing coordinates for
    increasing node number, define a 2D mesh in gmsh using curves that are
    oriented clockwise, or if you mirror a mesh. This is not a problem if
    the weak form consists of domain integrals only. However, if you also
    have boundary integrals in the weak form or want to compute reaction
    forces, this is a problem.

    Therefore, two logicals have been defined in limits_m:

     1. SET_ABSOLUTE_DETF, which takes the absolute value of detF always if
        set to .true.

     2. CHECK_POSITIVE_DETF, which tests the sign of detF and stops the program
        if a non-positive values is detected, if set to .true.
        The value of CHECK_POSITIVE_DETF is only relevant if
        SET_ABSOLUTE_DETF=.false.

    The previous default was
          SET_ABSOLUTE_DETF=.false.
          CHECK_POSITIVE_DETF=.false.
    whereas the defaults from now on are
          SET_ABSOLUTE_DETF=.true.
          CHECK_POSITIVE_DETF=.false.

    You can test your code for negative Jacobians in your mesh by setting
          SET_ABSOLUTE_DETF=.false.
          CHECK_POSITIVE_DETF=.true.
    If you get an error message saying detF<0 and you also apply boundary
    integrals (natural bc, slip, ...), you should check the correctness of
    the (sign of the) coefficients for the boundary integrals carefully.

  - Module sparse_m: new routine add_sparsematrix.

  Add-ons:

  - UMFPACK: give error message if symmetric matrix storage is used.

  Examples:

  - Modified the mesh of some 1D height function problems to have a
    positive Jacobian determinant (detF>0).

  Compatibility:

  - The infrastructure for blended meshes/elements is fully compatible
    on the user level for codes running with previous tfem versions.

  - On a lower level (components of structures, lower level interfaces)
    changes have been made that might affect users having lower level code
    in their own codes. Some notes on the structures mesh_t and
    geometry_t:

    * A structure of type mesh_t has acquired the components
        integer :: nblend = 0
        type(element_t), allocatable, dimension(:,:) :: element_blend
        integer, allocatable, dimension(:) :: nnodes_blend
        integer, allocatable, dimension(:) :: numnodtop
      where the first three are part of a basic mesh and need to be
      allocated and filled always. For a non-blend mesh the allocation
      and filling must be according to:
        allocate( mesh%element_blend ( mesh%nelgrp, 0 ) )
        allocate( mesh%nnodes_blend(2) ); mesh%nnodes_blend = [0,mesh%nnodes]
      The numnodtop component is only allocated and filled in fill_mesh_parts.
      Note, a mesh created with mesh_skeleton already contains the
      required additional components.

    * A structure of type geometry_t (curves,surfaces,volumes) has acquired
      the components
        integer :: nblend = 0
        type(element_t), allocatable, dimension(:) :: element_blend
        integer, allocatable, dimension(:) :: nnodes_blend
        integer, allocatable, dimension(:) :: numnodtop
      where the first three are part of a basic geometry and need to be
      allocated and filled always. For a non-blend mesh the allocation
      and filling must be according to:
        do i = 1, mesh%ncurves
          allocate(mesh%curves(i)%element_blend(0))
          allocate(mesh%curves(i)%nnodes_blend(2) )
          mesh%curves(i)%nnodes_blend = [0,mesh%curves(i)%nnodes]
        end do
      and similarly for the surfaces and volumes.
      The numnodtop component is only allocated and filled in fill_mesh_parts.
      Note, a geometry created with geometry_skeleton already contains the
      required additional components.

    * The component elnumnod of a structure of type geometry_t is not
      filled for basic geometries anymore, similar to elnumnod in a
      basic mesh. The value for elnumnod is now filled in
      fill_mesh_parts from the numnod values in the elements.

v2.4.3 (September 19, 2019):

  - New Gauss integration rules for a hexahedron in gauss_standard_numeric2_m
    in the routine Gauss_Legendre_numeric_hexahedron2. These can be used
    only by setting the variable GAUSS_RULE in the module limits_m.
    Although the number of integration points is less than the default product
    rules, they are also less accurate in that only terms x^k*y^l*z^m, with
    k+l+m<=p are exact for given order p. The product rules integrate
    x^k*y^l*z^m exact for k<=p, l<=p, m<=p. Early testing with biquadratic
    elements for poisson shows that the new rules require more integration
    points to obtain sufficient accuracy. More testing is needed, but for now
    the new rules are not recommended for standard finite elements.

Start tagging and summarizing changes between tags in this CHANGES file
because git commits (and documentation thereof) are mostly small incremental
changes.

Version x.y.z means:
  x: Major version number: increments when major new features have been
     implemented and/or incompatible changes have been necessary.
  y: Minor version number: increments when minor new features have been
     implemented and changes are backward compatible.
  z: Patch version number: backward compatible bug fixes and/or minor
     changes, such as new examples.

Note: we start with version 2.0.0 to signify the maturity of tfem and that
"1.0" has been reached years ago.
